### 1. Какие основные типы памяти существуют в архитектуре CUDA и чем они отличаются по скорости доступа?

В CUDA существует несколько типов памяти, которые отличаются по скорости, размеру и области видимости:

#### Иерархия памяти (от быстрой к медленной):

**1. Регистры (Registers)**
- Самая быстрая память
- Приватная для каждого потока
- Размер: ~64 KB на SM (streaming multiprocessor)
- Время доступа: 1 такт
- Использование: локальные переменные
```cuda
int x = 5;  // Хранится в регистре
```

**2. Разделяемая память (Shared Memory)**
- Очень быстрая память
- Общая для всех потоков в блоке
- Размер: 48-96 KB на блок
- Время доступа: ~5 тактов
- Использование: обмен данными между потоками блока
```cuda
__shared__ float sharedData[256];
```

**3. Локальная память (Local Memory)**
- Находится в глобальной памяти, но приватная для потока
- Используется когда не хватает регистров
- Скорость как у глобальной памяти (медленная)
- Использование: большие массивы и структуры в потоке

**4. Константная память (Constant Memory)**
- Только для чтения
- Кэшируется
- Размер: 64 KB
- Время доступа: ~5-100 тактов (зависит от кэша)
- Быстрая если все потоки читают одинаковый адрес
```cuda
__constant__ float constData[100];
```

**5. Текстурная память (Texture Memory)**
- Только для чтения
- Кэшируется, оптимизирована для 2D локальности
- Используется для изображений
- Время доступа: ~100-400 тактов

**6. Глобальная память (Global Memory)**
- Самая медленная, но самая большая
- Доступна всем потокам всех блоков
- Размер: гигабайты (вся память GPU)
- Время доступа: ~400-800 тактов
- Использование: входные/выходные данные
```cuda
float* deviceData;
cudaMalloc(&deviceData, size);
```

#### Сравнительная таблица:

| Тип памяти | Скорость | Размер | Видимость | Жизненный цикл |
|------------|----------|--------|-----------|----------------|
| Регистры | Очень быстро (1 такт) | ~32 KB | Поток | Поток |
| Shared | Быстро (5 тактов) | 48-96 KB | Блок | Блок |
| Local | Медленно (400+ тактов) | Зависит | Поток | Поток |
| Constant | Средне (5-100 тактов) | 64 KB | Грид | Программа |
| Texture | Средне (100-400 тактов) | Большой | Грид | Программа |
| Global | Медленно (400-800 тактов) | ГБ | Грид | Программа |

**Правило оптимизации:** Используйте самую быструю память, которая подходит для задачи!

### 2. В каких случаях использование разделяемой памяти позволяет ускорить выполнение CUDA-программы?

Разделяемая память (shared memory) дает ускорение в следующих случаях:

#### 1. **Переиспользование данных (Data Reuse)**

Когда несколько потоков читают одни и те же данные:

```cuda
// ПЛОХО: каждый поток читает из глобальной памяти
__global__ void bad(float* data) {
    int idx = threadIdx.x;
    float sum = data[0] + data[1] + data[2];  // 3 чтения глобальной памяти на поток!
}

// ХОРОШО: загружаем в shared memory один раз
__global__ void good(float* data) {
    __shared__ float sharedData[3];

    // Только первые 3 потока загружают данные
    if (threadIdx.x < 3) {
        sharedData[threadIdx.x] = data[threadIdx.x];
    }
    __syncthreads();

    // Все потоки читают из быстрой shared memory
    float sum = sharedData[0] + sharedData[1] + sharedData[2];
}
```

#### 2. **Обмен данными между потоками блока**

Когда потоки должны обмениваться результатами:

```cuda
__global__ void transpose(float* input, float* output) {
    __shared__ float tile[32][32];

    // Загружаем блок в shared memory
    tile[threadIdx.y][threadIdx.x] = input[...];
    __syncthreads();

    // Транспонируем через shared memory (избегаем некоалесцированного доступа)
    output[...] = tile[threadIdx.x][threadIdx.y];
}
```

#### 3. **Редукция (Reduction)**

Суммирование или поиск минимума/максимума:

```cuda
__global__ void reduce(float* input, float* output) {
    __shared__ float sdata[256];

    // Каждый поток загружает свой элемент
    sdata[threadIdx.x] = input[threadIdx.x];
    __syncthreads();

    // Складываем попарно в shared memory (быстро!)
    for (int s = blockDim.x / 2; s > 0; s >>= 1) {
        if (threadIdx.x < s) {
            sdata[threadIdx.x] += sdata[threadIdx.x + s];
        }
        __syncthreads();
    }
}
```

#### 4. **Свертка (Convolution)**

Когда соседние элементы используются многократно:

```cuda
__global__ void convolution(float* input, float* output) {
    __shared__ float shared[BLOCK_SIZE + 2 * RADIUS];

    // Загружаем данные с halo (соседние элементы)
    shared[threadIdx.x] = input[...];
    __syncthreads();

    // Применяем фильтр используя данные из shared memory
    float sum = 0;
    for (int i = -RADIUS; i <= RADIUS; i++) {
        sum += shared[threadIdx.x + i] * filter[i];
    }
}
```

#### 5. **Гистограммы**

Когда много потоков обновляют одни и те же счетчики:

```cuda
__global__ void histogram(int* input, int* output) {
    __shared__ int localHist[256];

    // Обнуляем локальную гистограмму
    if (threadIdx.x < 256) localHist[threadIdx.x] = 0;
    __syncthreads();

    // Обновляем локальную гистограмму (в shared memory - быстро)
    atomicAdd(&localHist[input[idx]], 1);
    __syncthreads();

    // Записываем в глобальную память один раз
    if (threadIdx.x < 256) {
        atomicAdd(&output[threadIdx.x], localHist[threadIdx.x]);
    }
}
```

#### Когда shared memory НЕ помогает:

- Данные используются только один раз каждым потоком
- Доступ уже коалесцированный и нет переиспользования
- Операции очень простые (например, просто копирование)
- Размер данных больше чем shared memory

**Ключевое правило:** Shared memory ускоряет когда есть переиспользование данных или обмен между потоками!

### 3. Как шаблон доступа к глобальной памяти влияет на производительность GPU-программы?

Шаблон доступа к памяти - один из главных факторов производительности GPU!

#### Коалесцированный доступ (БЫСТРО)

**Определение:** Соседние потоки в warp (32 потока) обращаются к соседним адресам в памяти.

```cuda
// ХОРОШИЙ паттерн - коалесцированный
__global__ void good(float* data) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    float value = data[idx];  // Поток 0 → data[0], поток 1 → data[1], ...
}
```

**Что происходит:**
- GPU объединяет 32 обращения в 1-2 транзакции памяти
- Пропускная способность: ~700 GB/s (максимум)

#### Некоалесцированный доступ (МЕДЛЕННО)

```cuda
// ПЛОХОЙ паттерн - stride (шаг)
__global__ void bad(float* data, int stride) {
    int idx = (blockIdx.x * blockDim.x + threadIdx.x) * stride;
    float value = data[idx];  // Поток 0 → data[0], поток 1 → data[1024], ...
}
```

**Что происходит:**
- GPU делает 32 отдельные транзакции для одного warp
- Пропускная способность: ~20 GB/s (в 35 раз медленнее!)

#### Основные паттерны:

**1. Последовательный доступ (ОТЛИЧНО)**
```cuda
data[idx], data[idx+1], data[idx+2], ...
```
- 1 транзакция на warp
- Максимальная производительность

**2. Доступ со stride (ПЛОХО)**
```cuda
data[0], data[1000], data[2000], ...
```
- 32 транзакции на warp
- Производительность падает в 10-30 раз

**3. Случайный доступ (ОЧЕНЬ ПЛОХО)**
```cuda
data[random_index]
```
- Невозможно предсказать
- Невозможно кэшировать
- Самый медленный вариант

**4. Broadcast (ХОРОШО для constant memory)**
```cuda
// Все потоки читают одинаковый адрес
float value = data[0];
```
- Эффективно для constant memory
- Неэффективно для global memory

#### Примеры влияния:

**Транспонирование матрицы:**
```cuda
// ПЛОХО: некоалесцированная запись
output[j * width + i] = input[i * width + j];

// ХОРОШО: используем shared memory для коалесцированного доступа
__shared__ float tile[32][32];
tile[threadIdx.y][threadIdx.x] = input[i * width + j];
__syncthreads();
output[j * width + i] = tile[threadIdx.x][threadIdx.y];
```

**Структуры (struct of arrays vs array of structs):**
```cuda
// ПЛОХО: Array of Structs (AoS)
struct Particle {
    float x, y, z;
    float vx, vy, vz;
};
Particle particles[N];
particles[idx].x;  // Некоалесцированный доступ!

// ХОРОШО: Struct of Arrays (SoA)
struct Particles {
    float x[N], y[N], z[N];
    float vx[N], vy[N], vz[N];
};
Particles p;
p.x[idx];  // Коалесцированный доступ!
```

#### Измеренная разница производительности:

| Паттерн | Скорость (GB/s) | Относительно |
|---------|-----------------|--------------|
| Коалесцированный | 700 | 1.0x (база) |
| Stride 2 | 350 | 0.5x |
| Stride 4 | 175 | 0.25x |
| Stride 32 | 22 | 0.03x (в 30 раз медленнее!) |
| Случайный | 10-50 | 0.01-0.07x |

**Вывод:** Оптимизация паттерна доступа к памяти может дать ускорение в 10-30 раз!

### 4. Почему одинаковый алгоритм на GPU может показывать разное время выполнения при разных способах обращения к памяти?

Причины различий во времени выполнения:

#### 1. **Аппаратная архитектура памяти**

GPU читает память блоками (cache lines), обычно по 128 или 256 байт:

```
Память: [0][1][2][3][4][5][6][7]...[127][128][129]...
        └──────── 1 cache line ───────┘
```

**Коалесцированный доступ:**
- Warp читает data[0-31] → 1 cache line → 1 транзакция

**Некоалесцированный доступ:**
- Warp читает data[0], data[128], data[256], ... → 32 разных cache lines → 32 транзакции

#### 2. **Латентность vs Пропускная способность**

GPU использует массовый параллелизм чтобы скрыть латентность:

```
Время = Латентность + (Объем_данных / Пропускная_способность)
```

**Коалесцированный доступ:**
- Пропускная способность: максимальная (~700 GB/s)
- Латентность скрыта другими потоками

**Некоалесцированный доступ:**
- Пропускная способность: минимальная (~20 GB/s)
- Латентность не скрыта (слишком много транзакций)

#### 3. **Эффективность кэша**

GPU имеет L1 и L2 кэш:

**Коалесцированный паттерн:**
```cuda
// Соседние потоки → соседние адреса → хороший кэш hit
data[idx]
```
- Кэш эффективен: ~80-90% hit rate
- Большинство данных из кэша (быстро)

**Некоалесцированный паттерн:**
```cuda
// Разбросанные адреса → плохой кэш hit
data[idx * stride]
```
- Кэш неэффективен: ~10-20% hit rate
- Большинство данных из глобальной памяти (медленно)

#### 4. **Количество транзакций памяти**

**Пример: 32 потока (1 warp) читают 32 float числа (128 байт)**

Коалесцированный:
```
data[0], data[1], data[2], ..., data[31]
→ 1 транзакция 128 байт
→ Время: 400 тактов
```

Stride 32:
```
data[0], data[32], data[64], ..., data[992]
→ 32 транзакции по 128 байт каждая
→ Время: 400 * 32 = 12800 тактов (в 32 раза дольше!)
```

#### 5. **Занятость (Occupancy)**

**При хорошем доступе к памяти:**
- Потоки быстро получают данные
- GPU может запускать больше блоков одновременно
- Высокая занятость = лучшее использование GPU

**При плохом доступе:**
- Потоки ждут данные из памяти
- Меньше блоков выполняется одновременно
- Низкая занятость = плохое использование GPU

#### Реальный пример из нашей задачи:

```cuda
// Задача: скопировать массив

// Версия 1: коалесцированный доступ
output[idx] = input[idx];
// Время: 1.2 мс

// Версия 2: stride доступ
int newIdx = (idx / 32) + (idx % 32) * (size / 32);
output[newIdx] = input[newIdx];
// Время: 35.8 мс (в 30 раз медленнее!)

// ОДИНАКОВЫЕ вычисления, разный паттерн доступа!
```

#### 6. **Memory Divergence**

Когда потоки в warp обращаются к разным частям памяти, GPU сериализует доступ:

```cuda
if (threadIdx.x < 16) {
    value = dataA[idx];  // Первая половина warp
} else {
    value = dataB[idx];  // Вторая половина warp
}
// GPU делает 2 последовательных обращения вместо 1 параллельного
```

**Вывод:** Паттерн доступа к памяти важнее чем алгоритм! Оптимизируйте память сначала, алгоритм потом.

### 5. Как размер блока потоков влияет на производительность CUDA-ядра?

Размер блока (threads per block) критически важен для производительности!

#### Основные концепции:

**Warp** = 32 потока, выполняемых одновременно на одном SM (streaming multiprocessor)

**Блок** = группа потоков (обычно 128-1024)

**Сетка** = набор всех блоков

#### Влияние размера блока:

#### 1. **Утилизация Warp**

Потоки выполняются группами по 32 (warp). Если блок не кратен 32, часть warp пустует:

```
Блок 32:  [████████████████] - 1 warp, 100% использование
Блок 64:  [████████████████][████████████████] - 2 warp, 100%
Блок 50:  [████████████████][██████░░░░░░░░░░] - 2 warp, 78% использование
Блок 100: [████████████████][████████████████][████░░░░░░░░░░░░] - 75%
```

**Правило:** Размер блока должен быть кратен 32!

#### 2. **Занятость (Occupancy)**

Occupancy = активные warp / максимум warp на SM

Больше активных warp → лучше скрывается латентность памяти

**Пример:** SM может выполнять 64 warp одновременно

| Размер блока | Warp в блоке | Блоков на SM | Активные warp | Occupancy |
|--------------|--------------|--------------|---------------|-----------|
| 32 | 1 | 64 | 64 | 100% |
| 64 | 2 | 32 | 64 | 100% |
| 128 | 4 | 16 | 64 | 100% |
| 256 | 8 | 8 | 64 | 100% |
| 512 | 16 | 4 | 64 | 100% |
| 1024 | 32 | 2 | 64 | 100% |

Но есть ограничения!

#### 3. **Ресурсы на блок**

Каждый SM имеет ограниченные ресурсы:
- Регистры (~65K на SM)
- Shared memory (48-96 KB на SM)
- Максимум потоков (1024-2048 на SM)

**Пример:** Если каждый поток использует 64 регистра:

| Размер блока | Регистров на блок | Блоков на SM | Реальная occupancy |
|--------------|-------------------|--------------|---------------------|
| 128 | 8192 | 8 | 100% |
| 256 | 16384 | 4 | 100% |
| 512 | 32768 | 2 | 100% |
| 1024 | 65536 | 1 | 50% (ограничение регистров!) |

#### 4. **Shared Memory ограничения**

```cuda
__shared__ float data[1024];  // 4 KB на блок

// Блок 128: 48KB / 4KB = 12 блоков → хорошо
// Блок 256: 48KB / 4KB = 12 блоков → хорошо
// Если shared memory больше:
__shared__ float bigData[8192];  // 32 KB на блок
// Блок 256: 48KB / 32KB = 1 блок → плохая occupancy!
```

#### 5. **Накладные расходы**

**Слишком маленький блок (< 128):**
- Больше блоков = больше накладных расходов на управление
- Хуже amortization latency

**Слишком большой блок (> 512):**
- Меньше блоков на SM = хуже occupancy при ограничениях ресурсов
- Меньше гибкости планировщика

#### Реальные измерения (из нашего эксперимента):

```
Сложение векторов (10М элементов):

Блок 32:   12.5 мс  (плохая утилизация SM)
Блок 64:   8.3 мс
Блок 128:  6.2 мс
Блок 256:  5.8 мс   ← ОПТИМУМ
Блок 512:  6.1 мс
Блок 1024: 6.8 мс   (ограничение ресурсов)
```

#### График зависимости:
```
Время
  │
  │  \
  │   \
  │    \___________
  │              ╱
  │            ╱
  │          ╱
  └─────────────────── Размер блока
   32  128  256  512  1024
        ↑
     Оптимум
```

#### Рекомендации:

1. **Начните с 256** - почти всегда хороший выбор
2. **Делайте кратным 32** (размер warp)
3. **Минимум 128** - иначе плохая утилизация
4. **Максимум 512-1024** - зависит от ресурсов
5. **Тестируйте!** - оптимум зависит от:
   - Количества регистров на поток
   - Использования shared memory
   - Сложности вычислений
   - Конкретного GPU

**Используйте CUDA Occupancy Calculator** для подбора оптимального размера!

### 6. Что такое варп и почему важно учитывать его при разработке CUDA-программ?

#### Что такое Warp?

**Warp** - это группа из 32 потоков, которые выполняются вместе **одновременно** на одном streaming multiprocessor (SM).

Это базовая единица выполнения в CUDA!

```
Блок 256 потоков = 8 warp
┌────────────────┐
│ Warp 0 (0-31)  │ ← выполняются одновременно
│ Warp 1 (32-63) │
│ Warp 2 (64-95) │
│ ...            │
│ Warp 7 (224-255)│
└────────────────┘
```

#### Как работает Warp?

Warp использует модель **SIMT** (Single Instruction, Multiple Threads):
- Все 32 потока выполняют **одну и ту же инструкцию**
- Но с **разными данными**

```cuda
// Инструкция: ADD
Поток 0:  a[0] = b[0] + c[0]
Поток 1:  a[1] = b[1] + c[1]
Поток 2:  a[2] = b[2] + c[2]
...
Поток 31: a[31] = b[31] + c[31]

→ Все 32 операции выполняются за 1 такт!
```

#### Проблемы связанные с Warp:

#### 1. **Warp Divergence (Дивергенция)**

Когда потоки в warp идут по разным путям в if-else:

```cuda
// ПЛОХО: warp divergence
if (threadIdx.x % 2 == 0) {
    // Четные потоки: путь A
    result = heavyCalculationA();
} else {
    // Нечетные потоки: путь B
    result = heavyCalculationB();
}

// Что происходит:
// Шаг 1: потоки 0,2,4,... выполняют путь A, остальные ждут
// Шаг 2: потоки 1,3,5,... выполняют путь B, остальные ждут
// Время = A + B (вместо max(A, B))
```

**Решение:** Организуйте код так чтобы весь warp шел по одному пути:

```cuda
// ХОРОШО: нет дивергенции
if (threadIdx.x < 16) {
    // Первые 16 потоков: путь A (warp 0 наполовину)
    result = heavyCalculationA();
} else {
    // Вторые 16 потоков: путь B (warp 0 наполовину)
    result = heavyCalculationB();
}
// Все равно есть дивергенция, но лучше делать так:

// ОТЛИЧНО: warp выполняют разные пути
int warpId = threadIdx.x / 32;
if (warpId == 0) {
    result = heavyCalculationA();  // Warp 0: все потоки путь A
} else {
    result = heavyCalculationB();  // Warp 1: все потоки путь B
}
```

#### 2. **Коалесцированный доступ к памяти**

Warp читает память вместе. Если потоки warp обращаются к соседним адресам:

```cuda
// ХОРОШО: коалесцированный доступ
int idx = blockIdx.x * blockDim.x + threadIdx.x;
float value = data[idx];

// Warp 0 читает:
// Поток 0  → data[0]
// Поток 1  → data[1]
// ...
// Поток 31 → data[31]
// → 1 транзакция памяти для всего warp!
```

```cuda
// ПЛОХО: некоалесцированный доступ
int idx = threadIdx.x * 1000;
float value = data[idx];

// Warp 0 читает:
// Поток 0  → data[0]
// Поток 1  → data[1000]
// Поток 31 → data[31000]
// → 32 транзакции памяти (в 32 раза медленнее!)
```

#### 3. **Размер блока должен быть кратен 32**

```cuda
// ПЛОХО: блок не кратен 32
dim3 block(100);  // 100 / 32 = 3.125 warp

// Что происходит:
// Warp 0: потоки 0-31   (32 потока) ✓
// Warp 1: потоки 32-63  (32 потока) ✓
// Warp 2: потоки 64-95  (32 потока) ✓
// Warp 3: потоки 96-99  (4 потока)  ✗ остальные 28 простаивают!

// ХОРОШО: блок кратен 32
dim3 block(128);  // 128 / 32 = 4 warp точно
```

#### 4. **__syncthreads() синхронизирует блок, не warp**

```cuda
// Warp всегда синхронны!
__global__ void kernel() {
    int val = data[threadIdx.x];

    // НЕ нужен __syncthreads() внутри warp
    // Все потоки warp уже синхронны

    int next = data[threadIdx.x + 1];  // OK внутри warp
}

// Но между warp нужна синхронизация:
__global__ void kernel() {
    __shared__ float shared[256];
    shared[threadIdx.x] = data[threadIdx.x];

    __syncthreads();  // Нужно! Ждем все warp блока

    float val = shared[threadIdx.x + 64];  // Может быть из другого warp
}
```

#### 5. **Warp-level Primitives**

CUDA предоставляет специальные функции для работы с warp:

```cuda
// Shuffle - обмен данными внутри warp БЕЗ shared memory
int value = 123;
int neighbor = __shfl_down_sync(0xffffffff, value, 1);  // Получить значение от соседа

// Warp vote functions
int allTrue = __all_sync(0xffffffff, condition);   // Все потоки true?
int anyTrue = __any_sync(0xffffffff, condition);   // Хотя бы один true?
unsigned mask = __ballot_sync(0xffffffff, condition);  // Битмаска кто true

// Warp-level reduction
int sum = value;
sum += __shfl_down_sync(0xffffffff, sum, 16);
sum += __shfl_down_sync(0xffffffff, sum, 8);
sum += __shfl_down_sync(0xffffffff, sum, 4);
sum += __shfl_down_sync(0xffffffff, sum, 2);
sum += __shfl_down_sync(0xffffffff, sum, 1);
// Поток 0 теперь имеет сумму всех 32 потоков warp!
```

#### Практические рекомендации:

1. **Размер блока кратен 32**
2. **Избегайте дивергенции** - организуйте условия так чтобы весь warp шел по одному пути
3. **Коалесцированный доступ** - соседние потоки → соседние адреса
4. **Используйте warp-level функции** вместо shared memory где возможно
5. **Помните:** warp - это единица выполнения, блок - единица организации

**Ключевая мысль:** GPU не выполняет отдельные потоки, он выполняет warp целиком!

### 7. Какие факторы необходимо учитывать при выборе конфигурации сетки и блоков потоков?

При выборе конфигурации нужно балансировать много факторов!

#### 1. **Размер данных**

Нужно достаточно потоков чтобы обработать все данные:

```cuda
int size = 1000000;
int blockSize = 256;
int gridSize = (size + blockSize - 1) / blockSize;  // Округление вверх

// gridSize = 3907 блоков
// Всего потоков = 3907 * 256 = 1000192 (чуть больше чем нужно)
```

#### 2. **Количество SM (Streaming Multiprocessors)**

```cuda
cudaDeviceProp prop;
cudaGetDeviceProperties(&prop, 0);

int numSM = prop.multiProcessorCount;  // Например, 80 SM

// Минимум блоков = 2-4 на SM для хорошей занятости
int minBlocks = numSM * 2;  // 160 блоков минимум
```

**Правило:** Число блоков >> число SM

Почему? Планировщик GPU переключает блоки когда они ждут память.

#### 3. **Максимумы GPU**

```cuda
int maxThreadsPerBlock = prop.maxThreadsPerBlock;     // 1024
int maxBlocksPerSM = prop.maxThreadsPerMultiProcessor / blockSize;

// Проверяем ограничения:
if (blockSize > maxThreadsPerBlock) {
    // Ошибка! Блок слишком большой
}
```

#### 4. **Регистры**

Каждый поток использует регистры. Если их не хватает:

```cuda
// Пример: SM имеет 65536 регистров
// Каждый поток использует 32 регистра

int registersPerThread = 32;
int registersPerBlock = blockSize * registersPerThread;

// blockSize = 256: 256 * 32 = 8192 регистров на блок
//   → 65536 / 8192 = 8 блоков на SM ✓

// blockSize = 1024: 1024 * 32 = 32768 регистров на блок
//   → 65536 / 32768 = 2 блока на SM ✗ плохая занятость!
```

**Решение:** Используйте меньше регистров или меньший размер блока.

```cuda
// Компиляция с ограничением регистров:
// nvcc -maxrregcount=32 ...
```

#### 5. **Shared Memory**

```cuda
__shared__ float sharedData[1024];  // 4 KB на блок

// SM имеет 48 KB shared memory
// 48 KB / 4 KB = 12 блоков на SM максимум

// Если blockSize = 128:
// 12 блоков * 128 потоков = 1536 активных потоков
// Максимум 2048 на SM
// Occupancy = 1536 / 2048 = 75% ✓

// Если нужно больше occupancy - уменьшить shared memory
```

#### 6. **Размер Warp (всегда 32)**

```cuda
// ПЛОХО: не кратно 32
int blockSize = 100;  // 100 / 32 = 3.125 warp, потери 28 потоков

// ХОРОШО: кратно 32
int blockSize = 128;  // 128 / 32 = 4 warp, 0 потерь
```

#### 7. **Характер задачи**

**Memory-bound задачи** (ограничены памятью):
- Много чтений/записей, мало вычислений
- Пример: копирование, сложение векторов
- Стратегия: больше потоков, меньше регистров, коалесцированный доступ

```cuda
// blockSize = 256-512
// Много блоков для скрытия латентности памяти
```

**Compute-bound задачи** (ограничены вычислениями):
- Много вычислений на каждый элемент
- Пример: матричное умножение, FFT
- Стратегия: оптимальный баланс, использовать shared memory

```cuda
// blockSize = 128-256
// Используем shared memory для переиспользования данных
```

#### 8. **Occupancy (Занятость)**

Occupancy = активные warp / максимум warp на SM

```
Высокая occupancy (> 50%):
+ Лучше скрывается латентность памяти
+ Больше гибкости планировщика
- Может не хватить ресурсов (регистры, shared memory)

Низкая occupancy (< 25%):
+ Больше ресурсов на поток
- Хуже скрывается латентность
```

**Не всегда нужна 100% occupancy!** Иногда лучше 50% occupancy с оптимизированным кодом.

#### Практический алгоритм выбора:

```python
# Шаг 1: Определить размер данных
size = 10000000

# Шаг 2: Выбрать начальный blockSize
blockSize = 256  # Хорошая отправная точка

# Шаг 3: Вычислить gridSize
gridSize = (size + blockSize - 1) // blockSize

# Шаг 4: Проверить ограничения
if blockSize % 32 != 0:
    # Округлить до кратного 32
    blockSize = ((blockSize + 31) // 32) * 32

# Шаг 5: Проверить ресурсы
registersNeeded = blockSize * registersPerThread
sharedMemoryNeeded = blockSize * sharedMemoryPerThread

if registersNeeded > registersPerSM:
    blockSize = registersPerSM // registersPerThread

if sharedMemoryNeeded > sharedMemoryPerSM:
    blockSize = sharedMemoryPerSM // sharedMemoryPerThread

# Шаг 6: Тестировать разные конфигурации!
for bs in [128, 256, 512]:
    time = benchmark(bs)
    print(f"BlockSize {bs}: {time} ms")
```

#### Инструменты для подбора:

1. **CUDA Occupancy Calculator**
   - Excel таблица от NVIDIA
   - Показывает occupancy для разных конфигураций

2. **CUDA Profiler (nvprof/Nsight)**
   ```bash
   nvprof --metrics achieved_occupancy ./program
   ```

3. **Runtime API**
   ```cuda
   int minGridSize, blockSize;
   cudaOccupancyMaxPotentialBlockSize(&minGridSize, &blockSize, myKernel, 0, 0);
   ```

#### Чеклист выбора конфигурации:

- ✓ blockSize кратен 32
- ✓ blockSize >= 128 (обычно)
- ✓ blockSize <= 512-1024 (зависит от ресурсов)
- ✓ gridSize >= 2 * число SM
- ✓ gridSize * blockSize >= размер данных
- ✓ Хватает регистров
- ✓ Хватает shared memory
- ✓ Occupancy >= 25-50%
- ✓ Протестировано несколько вариантов!

**Главное правило:** Не существует универсальной конфигурации. Тестируйте и профилируйте!

### 8. Почему оптимизация CUDA-программы часто начинается с анализа работы с памятью, а не с изменения алгоритма?

Это ключевой вопрос оптимизации GPU!

#### Главная причина: Memory Wall (Стена памяти)

GPU имеет огромную вычислительную мощность, но память не успевает за ней:

```
GPU (RTX 4090):
- Вычисления: 82 TFLOPS (триллионов операций/сек)
- Память: 1 TB/s (терабайт/сек)

Соотношение: 82 TFLOPS / 1 TB/s = 82 операций на байт
```

Это означает: **Для каждого байта данных GPU может сделать ~80 операций**

#### Arithmetic Intensity (Вычислительная интенсивность)

```
AI = Количество операций / Количество байт из памяти
```

**Если AI < 80:** программа ограничена памятью (memory-bound)
**Если AI > 80:** программа ограничена вычислениями (compute-bound)

#### Большинство программ - memory-bound!

```cuda
// Пример 1: Сложение векторов (AI = 0.125)
C[i] = A[i] + B[i];
// Операций: 1 (сложение)
// Байт: 3 * 4 = 12 (3 float по 4 байта)
// AI = 1 / 12 = 0.08 операций/байт
// Ограничено памятью! Вычисления используются на 0.1%!

// Пример 2: Умножение матриц (AI = N)
for (int k = 0; k < N; k++)
    C[i][j] += A[i][k] * B[k][j];
// Операций: 2N (умножение + сложение, N раз)
// Байт: (2N + 1) * 4 (читаем 2N элементов, пишем 1)
// AI ≈ N/2 операций/байт
// Для N=1000: AI=500 - compute-bound! ✓
```

#### Почему сначала оптимизировать память:

#### 1. **Больший потенциал ускорения**

```
Пример: Копирование массива

Версия 1: Некоалесцированный доступ
- Время: 100 мс
- Пропускная способность: 10 GB/s (1% от максимума!)

Версия 2: Коалесцированный доступ
- Время: 2 мс (ускорение 50x!)
- Пропускная способность: 500 GB/s (50% от максимума)

Версия 3: Другой алгоритм (но некоалесцированный)
- Время: 95 мс
- Ускорение всего 5%!

Оптимизация памяти дала 50x, алгоритма - только 5%!
```

#### 2. **Проще найти проблемы**

```bash
# Профилирование памяти
nvprof --metrics gld_efficiency,gst_efficiency ./program

# Показывает:
# gld_efficiency = 25%  ← Плохая эффективность чтения!
# gst_efficiency = 30%  ← Плохая эффективность записи!

# Сразу видно где проблема
```

Проблемы с алгоритмом найти сложнее.

#### 3. **Память - главный bottleneck**

Распределение времени типичной CUDA программы:

```
Память:        70% ████████████████████████████
Вычисления:    20% ████████
Синхронизация: 10% ████
```

Оптимизация 70% важнее чем оптимизация 20%!

#### 4. **Простые оптимизации памяти дают большой эффект**

**Коалесцированный доступ:**
```cuda
// Было
data[threadIdx.x * 1000]

// Стало
data[threadIdx.x]

// 1 строка кода → ускорение 20x!
```

**Использование shared memory:**
```cuda
// Было
for (int i = 0; i < N; i++)
    sum += globalData[idx];  // N чтений из медленной памяти

// Стало
__shared__ float sharedData[N];
if (threadIdx.x == 0) {
    for (int i = 0; i < N; i++)
        sharedData[i] = globalData[i];  // 1 чтение
}
__syncthreads();
for (int i = 0; i < N; i++)
    sum += sharedData[idx];  // N чтений из быстрой памяти

// Ускорение 10x!
```

#### 5. **Алгоритм может быть оптимальным, но реализация плохой**

```cuda
// Оптимальный алгоритм O(n log n)
// Но плохая реализация:

for (int i = 0; i < n; i++) {
    // Случайный доступ к памяти
    int idx = randomIndex[i];
    result[idx] = process(data[idx]);
}

// Пропускная способность: 20 GB/s (2% от максимума)
// Время: 1000 мс

// Та же сложность O(n log n), но с хорошим доступом:
for (int i = 0; i < n; i++) {
    // Последовательный доступ
    result[i] = process(data[i]);
}

// Пропускная способность: 700 GB/s (70% от максимума)
// Время: 30 мс (ускорение 33x!)

// Алгоритм тот же, доступ к памяти разный!
```

#### 6. **Иерархия оптимизаций**

Правильный порядок оптимизации GPU программ:

```
1. Коалесцированный доступ к памяти         (10-50x ускорение)
   ↓
2. Использование shared memory              (2-10x ускорение)
   ↓
3. Оптимизация конфигурации блоков         (1.5-3x ускорение)
   ↓
4. Минимизация дивергенции warp            (1.2-2x ускорение)
   ↓
5. Оптимизация вычислений                  (1.1-1.5x ускорение)
   ↓
6. Изменение алгоритма                     (зависит от задачи)
```

Начинать снизу неэффективно!

#### Реальный пример оптимизации:

```
Задача: Обработка изображения 4K (4096x2160)

Версия 1: Наивная реализация
- Некоалесцированный доступ
- Только global memory
- Время: 500 мс

Версия 2: Коалесцированный доступ
- Исправили паттерн доступа
- Время: 25 мс (ускорение 20x!)

Версия 3: + Shared memory
- Используем shared memory для фильтров
- Время: 8 мс (ускорение 3x от версии 2)

Версия 4: + Оптимизация блоков
- Подобрали оптимальный размер блока
- Время: 5 мс (ускорение 1.6x от версии 3)

Версия 5: + Другой алгоритм
- Изменили алгоритм фильтрации
- Время: 4 мс (ускорение 1.25x от версии 4)

Итого: 500 мс → 4 мс = ускорение 125x!
Из них:
- Память: 100x (80% всего ускорения!)
- Алгоритм: 1.25x (только 20% ускорения)
```

#### Как определить что программа memory-bound:

```bash
# Профилирование
nvprof --metrics achieved_occupancy,gld_throughput,gst_throughput ./program

# Если:
# - gld_throughput близко к максимуму → memory-bound
# - achieved_occupancy низкая → проблемы с ресурсами
# - Время на memory operations > 50% → memory-bound
```

#### Вывод:

**Память - это bottleneck номер 1 в GPU программах!**

Оптимизация памяти:
- ✓ Дает наибольшее ускорение (10-50x)
- ✓ Проще найти и исправить
- ✓ Должна быть сделана ПЕРВОЙ
- ✓ Часто достаточно для хорошей производительности

Оптимизация алгоритма:
- Важна, но ПОСЛЕ оптимизации памяти
- Дает меньшее ускорение (1.2-3x обычно)
- Сложнее реализовать

**Правило:** Сначала сделайте простой алгоритм с отличным доступом к памяти, потом думайте о сложном алгоритме!
